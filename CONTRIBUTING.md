# Contributing Guide

Thank you for contributing. Please read the following guidelines before submitting changes.

## Development Environment

### Go Toolchain

Go 1.26 or newer. `go.mod` declares the minimum, and the toolchain will fetch a matching version automatically if yours is older.

The floor tracks the Go releases that still receive security fixes, rather than the oldest release the code could compile on. Go supports a major version until two newer ones exist, and `govulncheck` runs against the floor in CI — so a floor that has gone end-of-life reports standard-library vulnerabilities that no change to this SDK can fix.

The SDK itself has **no dependencies** outside the standard library, and that is deliberate — a client library should not decide a caller's dependency tree for them. Please do not add one without discussing it first.

### Development Tools

```bash
go install honnef.co/go/tools/cmd/staticcheck@v0.8.1  # Static analysis
cargo install --locked typos-cli                      # Spell checking
cargo install --locked git-cliff                      # Changelog generation
```

Staticcheck is pinned to the version CI runs, so that a release adding new checks cannot fail a pull request that was clean locally. Bump it here and in `.github/workflows/ci.yml` together.

## Local Checks

Before submitting changes, make sure these pass:

```bash
gofmt -l .                       # Must print nothing
go vet ./...
staticcheck ./...
go test -race ./...
typos
```

Examples are excluded from the package build by a `//go:build ignore` tag, so `go test ./...` does not compile them. Check them explicitly:

```bash
find examples -name '*.go' -exec go build -o /dev/null {} \;
```

## Adding A Task Type

Adding a task type touches five places, and the test suite fails if any of them is missed:

1. `tasktype.go` — the constant, plus entries in `KnownTaskTypes` and, if applicable, `syncTaskTypes`
2. `tasks_<vendor>.go` — the request model, with wire names copied byte for byte from the task catalog
3. `solutions.go` — the solution model, unless an existing one already fits
4. `solvers.go` — one convenience method, named `Solve<X>` to match `TaskType<X>`
5. `examples/<vendor>/<wire_name>.go` — a runnable example, plus a line in both `examples/README*.md`

Then add the model to the tables in `tasks_test.go` and `solutions_test.go`. Those tables are what stands between a mistyped wire name and a task that fails for no visible reason.

## Testing

- HTTP tests run against `httptest.Server`. **Never** point a test at the real API: creating a task is billed.
- Table-driven tests are preferred; name the subtests after what they assert rather than after the input.
- Line coverage should stay at or above 80%, with the transport and error-mapping paths close to complete.

## Commit Convention

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

| Type | Description |
|------|-------------|
| `feat:` | New feature |
| `fix:` | Bug fix |
| `docs:` | Documentation change |
| `refactor:` | Refactor that is neither a feature nor a bug fix |
| `perf:` | Performance improvement |
| `test:` | Test-related change |
| `chore:` | Build, toolchain, or miscellaneous maintenance |

The changelog is generated by git-cliff from commit history, so keep commit messages consistent.

## Branches And Pull Requests

- Create feature branches from `main`.
- Keep each pull request focused on a single topic.
- Pull requests must pass CI checks, including vet, staticcheck, test, and typos.

## Releasing

Versions follow [SemVer](https://semver.org/). Adding a task type, adding an optional field to a request model, adding an error category, or adding a solution model are **not** breaking changes — the type design is built to keep it that way.

To release, bump `Version` in `version.go`, then push a matching `vX.Y.Z` tag. The release workflow verifies the two agree and generates the release notes from commit history. Go modules are distributed straight from the tag, so there is nothing to upload.
